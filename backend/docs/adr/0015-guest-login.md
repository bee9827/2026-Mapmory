# ADR 0015. 게스트 로그인은 신원 확인 단계만 분기하고 인증 파이프라인을 재사용한다

- 상태: 제안 (초안 — 아래 "결정이 필요한 사항" 확정 후 채택)
- 날짜: 2026-08-25
- 관련: ADR 0009, ADR 0010, ADR 0011

---

## 문제

"로그인부터 하라고 하면 그냥 나간다"는 피드백이 있었다. 카카오 로그인이 첫 관문이면
서비스를 보기도 전에 이탈한다. 로그인 없이 기록을 남겨보고, 마음에 들면 그때 계정을
연결하는 경로가 필요하다.

이때 위험한 선택은 "게스트"를 별도의 인증 체계로 만드는 것이다. 토큰 형식이 갈라지고,
인증 필터가 두 종류를 구분하기 시작하며, 보호 API가 회원 종류를 알아야 하는 순간
인증 코드 전반이 복잡해진다. **어디까지 기존 구조를 재사용하고 어디만 분기할지**를
먼저 정해야 한다.

## 현재 인증 흐름

로그인은 세 단계로 나뉜다.

```
[1] 신원 확인          [2] 회원 결정                [3] 토큰 발급
카카오 access token →  (KAKAO, 회원번호)로        → access  : JWT(sub=member.id), 30분, 무상태
/v2/user/me 호출       find-or-create              refresh : SecureRandom 원문,
                                                             DB엔 SHA-256 해시 + 만료(14일)
```

로그인 이후의 모든 흐름은 **[3]의 산출물만** 사용한다.

- 보호 API: `JwtAuthenticationFilter` → `JwtProvider.parseMemberId` → SecurityContext에 `Long memberId`
  → `LoginMemberArgumentResolver`가 `Member` 주입
- 재발급: `RefreshTokenService.validateAndRevoke`(비관적 락·회전·재사용 감지) → 새 access·refresh
- 로그아웃: `revoke`로 `revoked_at` 기록

즉 **인증 경로에 "카카오"라는 개념은 [1] 이후 어디에도 없다.** `JwtProvider`도 인증 필터도
`sub`에 담긴 `member.id`만 본다. 이 사실이 이번 결정의 출발점이다.

## 결정

### [1] 신원 확인 단계만 분기한다

게스트 로그인은 [1]을 "카카오에 물어본다"에서 "서버가 식별자를 발급한다"로 바꾸는 것이 전부다.
[2]와 [3], 그리고 로그인 이후의 모든 흐름은 그대로 쓴다.

```
POST /api/v1/auth/login/guest     (요청 본문 없음)
→ 200 { "data": { "accessToken", "refreshToken", "isNewMember": true } }
```

컴포넌트별 영향은 다음과 같다.

| 구성 요소 | 게스트 도입 시 |
| --- | --- |
| `SecurityConfig` | 변경 없음 (`POST /api/v1/auth/**` 가 이미 permitAll) |
| `JwtAuthenticationFilter` | 변경 없음 |
| `JwtProvider` | 변경 없음 (`sub` = `member.id`) |
| `LoginMemberArgumentResolver` | 변경 없음 |
| `RefreshTokenService` | 변경 없음 (발급·회전·폐기·재사용 감지 그대로) |
| 보호 API 전체 | 변경 없음 |
| `AuthProvider` | `GUEST` 값 추가 |
| `AuthController` / `AuthService` | 게스트 로그인 진입점 추가 |
| DB 스키마 | 변경 없음 |

응답 형태(`LoginResponse`)도 카카오 로그인과 동일하게 둔다. 클라이언트가 로그인 종류에 따라
다른 저장·갱신 로직을 갖지 않게 하기 위해서다.

### 게스트의 "기기에 저장하는 비밀값"은 refresh token이 맡는다

앱에서 기기 식별자를 받지 않는다. 서버가 `UUID.randomUUID()`로 `provider_id`를 만들고,
세션 유지는 기존 refresh token이 담당한다.

이미 [3]에 "클라이언트에만 원문을 주고 서버는 해시만 보관하며, 회전·폐기·재사용 감지가 되는"
장치가 있다. 게스트 전용 키를 새로 정의하면 이 장치를 처음부터 다시 만드는 셈이 된다.

### 게스트도 `member` 테이블에 저장한다

| 컬럼 | 게스트 | 카카오 회원 |
| --- | --- | --- |
| `provider` | `GUEST` | `KAKAO` |
| `provider_id` | 서버 발급 UUID | 카카오 회원번호 |

`uk_member_provider UNIQUE (provider, provider_id)`(V12)를 그대로 쓴다. **마이그레이션이 없다.**
[2] 단계의 `findByProviderAndProviderId` 도 그대로 재사용된다.

### 승격은 같은 member 행에서 provider를 교체한다

게스트 상태에서 카카오 로그인을 하면 새 회원을 만들지 않고, 기존 게스트 행의
`provider`·`provider_id`를 카카오 값으로 갱신한다.

```
POST /api/v1/auth/login/kakao
Authorization: Bearer {게스트 accessToken}     ← 있으면 승격 시도
```

`travel_record`·`tag` 는 모두 `member_id`를 참조하므로 **데이터를 한 건도 옮기지 않는다.**
게스트를 별도 테이블로 분리했다면 여기서 전 테이블 마이그레이션이 필요했을 것이다.
이것이 게스트를 `member`에 통합하는 결정의 핵심 근거다.

승격 요청은 인증이 필요 없는 경로(`permitAll`)로 들어오지만, `JwtAuthenticationFilter`는
헤더가 있으면 permitAll 경로에서도 SecurityContext를 채운다. 따라서 승격 여부 판단에
별도의 필터나 인가 규칙이 필요하지 않다.

## 결정이 필요한 사항

제품 결정이므로 팀에서 확정한 뒤 본 ADR을 갱신하고 상태를 "채택"으로 바꾼다.

### 1. 승격하려는 카카오 계정으로 이미 가입한 회원이 있으면

| 안 | 동작 | 평가 |
| --- | --- | --- |
| A. 기존 계정 우선 | 기존 카카오 회원으로 로그인시키고 게스트 데이터는 폐기 | 단순. 앱에서 **사전 경고 필수** |
| B. 병합 | 게스트의 기록을 기존 회원으로 이전 후 게스트 행 삭제 | 사용자 친화적. 중복 처리·실패 롤백 등 복잡도 상승 |

MVP 범위에서는 A를 권장한다.

### 2. 게스트의 refresh 만료

게스트는 로그인 수단이 없어 **refresh가 만료되면 복구할 방법이 없다.**

현재 구현은 회전할 때마다 새 토큰에 `현재시각 + 14일`을 부여한다(`RefreshTokenService#issue`).
즉 이미 sliding 방식이며, 앱을 쓰는 동안 만료는 계속 뒤로 밀린다. 실제로 만료되는 경우는
**14일 연속 미접속**뿐이다. 따라서 결정할 것은 게스트에게 더 긴 미접속 허용 기간을 줄지 하나다.

| 안 | 동작 | 평가 |
| --- | --- | --- |
| A. 현행 유지 (14일) | 추가 구현 없음 | 2주간 앱을 열지 않으면 기록이 사라진다 |
| B. 게스트만 장기 만료 | `jwt.guest-refresh-token-validity` 분리 (180일 등) | 설정 분기 하나. 방치된 게스트 행이 오래 남아 정리 배치의 필요가 커진다 |

## 검토한 대안

### 게스트 전용 토큰 체계를 따로 만든다

채택하지 않았다. 인증 필터가 토큰 종류를 구분해야 하고, 보호 API마다 "게스트도 되는가"를
판단하는 코드가 번진다. 지금은 `sub`에 `member.id` 하나만 담겨 있어 인증 계층이 회원 종류를
전혀 모르는데, 이 단순함을 잃는 대가가 얻는 것보다 크다.

### 앱이 생성한 기기 UUID를 받아 게스트를 식별

채택하지 않았다. 그 UUID가 사실상 비밀번호가 되는데, 서버는 그것이 실제로 그 기기에서 왔는지
검증할 수 없다. 로그·백업·크래시 리포트로 한 번 유출되면 계정이 그대로 탈취된다.
클라이언트가 만드는 값이라 충돌·조작 가능성도 남는다.

`ANDROID_ID` 같은 OS 기기 식별자는 추가로, 앱을 삭제해도 값이 유지되어
"지우고 다시 깔았는데 예전 데이터가 돌아온다"는 문제와 개인정보 취급 이슈를 만든다.

### 게스트 전용 테이블을 분리

채택하지 않았다. 회원과 게스트의 도메인 속성이 사실상 같고, 승격 시 게스트가 만든 모든
데이터를 옮겨야 한다. `member` 통합이면 컬럼 두 개 갱신으로 끝난다.

### 로그인 없이 앱 로컬에만 저장

채택하지 않았다. 서버 계정이 없으면 기록이 기기에만 남아, 나중에 계정을 연결할 때 옮길
대상이 앱 내부에만 존재한다. 동기화 코드를 따로 만들어야 하고 기기 변경 시 유실된다.

## 결과

### 장점

- 첫 화면에서 로그인을 요구하지 않아 이탈 지점을 제거한다.
- 인증 계층이 회원 종류를 모르는 상태를 유지한다. 보호 API·필터·토큰 코드가 그대로다.
- 승격이 컬럼 갱신으로 끝나 데이터 이전이 없다.
- 신규 코드가 엔드포인트 1개와 enum 값 1개뿐이고, 마이그레이션이 없다.

### 비용과 주의점

- **무제한 계정 생성이 가능하다.** 인증 없이 호출되는 엔드포인트이므로 rate limit이 필요하다.
  특히 `POST /uploads/presigned-urls`가 열려 있어 S3 비용 어뷰징 경로가 된다.
- 한 번 쓰고 버려진 게스트 행이 누적된다. 정리(purge) 배치가 후속 과제다
  (ADR 0011의 refresh 정리 배치와 함께 다룰 수 있다).
- 앱 삭제 시 refresh token이 사라져 기록을 복구할 수 없다. 온보딩에서 명시해야 한다.
- 게스트 비율이 높아지면 `member` 행 수가 실사용자 수보다 훨씬 커진다. 지표를 볼 때
  `provider`로 구분해야 한다.
