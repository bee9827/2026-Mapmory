# ADR 0015. 게스트 로그인은 서버가 식별자를 발급하고, 회원으로 승격한다

- 상태: 제안 (초안 — 아래 "결정이 필요한 사항" 확정 후 채택)
- 날짜: 2026-08-25
- 관련: ADR 0010, ADR 0011

---

## 문제

"로그인부터 하라고 하면 그냥 나간다"는 피드백이 있었다. 카카오 로그인 화면이 첫 관문이면
서비스를 보기도 전에 이탈한다. 로그인 없이 여행 기록을 남겨보고, 마음에 들면 그때 계정을
연결하는 경로가 필요하다.

정해야 할 것은 세 가지다.

1. 로그인하지 않은 사용자를 **무엇으로 식별**할 것인가.
2. 그 식별자를 **누가 만들** 것인가 (앱 / 서버).
3. 게스트가 나중에 카카오 로그인하면 그동안 쌓은 기록을 **어떻게 이어줄** 것인가.

## 결정

### 게스트도 Member로 저장한다 (별도 테이블을 만들지 않는다)

`AuthProvider`에 `GUEST`를 추가하고, 게스트를 일반 회원과 같은 `member` 테이블에 저장한다.

| 컬럼 | 게스트 | 카카오 회원 |
| --- | --- | --- |
| `provider` | `GUEST` | `KAKAO` |
| `provider_id` | 서버가 발급한 UUID | 카카오 회원번호 |

`uk_member_provider UNIQUE (provider, provider_id)`(V12)가 이미 있어 스키마 제약은 그대로 쓴다.
필요한 변경은 enum 값 추가뿐이며, **마이그레이션이 필요 없다.**

별도의 `guest` 테이블을 만들지 않는 이유는 승격 때문이다. 아래를 참고한다.

### 식별자는 서버가 발급한다. 앱이 만든 기기 식별자를 받지 않는다

```
POST /api/v1/auth/login/guest     (요청 본문 없음)
→ 200 { "data": { "accessToken", "refreshToken", "isNewMember": true } }
```

서버가 `Member(GUEST, UUID.randomUUID())`를 만들고, 카카오 로그인과 **동일한 응답 형태**로
access·refresh를 발급한다. 앱은 refresh token만 저장하면 되고, 그 토큰이 곧 게스트의 신원이다.

세션 유지에 필요한 "기기에 저장하는 비밀값" 역할은 **이미 refresh token이 수행하고 있다.**
별도의 게스트 키를 새로 정의하지 않는다.

- 발급·회전·폐기·재사용 감지는 `RefreshTokenService`를 그대로 재사용한다 (ADR 0011).
- `JwtProvider`는 `sub`에 `member.id`만 담으므로, 보호 API는 게스트와 회원을 구분하지 않는다.
  **기존 API 코드는 변경되지 않는다.**

### 게스트 → 카카오 승격은 같은 member 행에서 provider를 교체한다

게스트 상태에서 카카오 로그인을 하면, 새 회원을 만들지 않고 **기존 게스트 member 행의
`provider`·`provider_id`를 카카오 값으로 갱신한다.**

```
POST /api/v1/auth/login/kakao
Authorization: Bearer {게스트 accessToken}     ← 있으면 승격 시도
```

`travel_record`, `tag` 등은 모두 `member_id`를 참조하므로 **데이터를 한 건도 옮기지 않는다.**
게스트를 별도 테이블로 분리했다면 여기서 전 테이블 마이그레이션이 필요했을 것이다.
이것이 게스트를 `member`에 통합하는 결정의 핵심 근거다.

## 결정이 필요한 사항

이 두 가지는 제품 결정이므로 팀에서 확정한 뒤 본 ADR을 갱신하고 상태를 "채택"으로 바꾼다.

### 1. 승격하려는 카카오 계정으로 이미 가입한 회원이 있으면

| 안 | 동작 | 평가 |
| --- | --- | --- |
| A. 기존 계정 우선 | 기존 카카오 회원으로 로그인시키고 게스트 데이터는 폐기 | 단순. 앱에서 **사전 경고 필수** |
| B. 병합 | 게스트의 기록을 기존 회원으로 이전 후 게스트 행 삭제 | 사용자 친화적. 중복 처리·실패 시 롤백 등 복잡도 상승 |

MVP 범위에서는 A를 권장한다. 대신 "이미 가입한 계정입니다. 지금까지의 기록은 사라집니다"를
로그인 전에 안내해야 한다.

### 2. 게스트의 refresh 만료

게스트는 로그인 수단이 없어 **refresh가 만료되면 복구할 방법이 없다.** 현재 값(14일)을 그대로
적용하면 2주간 앱을 열지 않은 사용자의 기록이 사라진다.

| 안 | 동작 |
| --- | --- |
| A. 게스트만 장기 만료 | 게스트 refresh는 180일 등 별도 값 적용 |
| B. 사용할 때마다 갱신 | 회전 시 만료를 연장(sliding). 활성 사용자는 사실상 만료 없음 |

## 검토한 대안

### 앱이 생성한 기기 UUID를 받아 게스트를 식별

채택하지 않았다. 그 UUID가 사실상 비밀번호가 되는데, 서버는 그것이 실제로 그 기기에서 왔는지
검증할 수 없다. 로그·백업·크래시 리포트로 한 번 유출되면 계정이 그대로 탈취된다.
클라이언트가 만드는 값이라 충돌·조작 가능성도 남는다.

`ANDROID_ID` 같은 OS 기기 식별자는 추가로, 앱을 삭제해도 값이 유지되어
"지우고 다시 깔았는데 예전 데이터가 돌아온다"는 문제와 개인정보 취급 이슈를 만든다.

### 게스트 전용 테이블을 분리

채택하지 않았다. 회원과 게스트의 도메인 속성이 사실상 같고, 승격 시 게스트가 만든 모든
데이터를 회원 쪽으로 옮겨야 한다. `member` 통합이면 컬럼 두 개 갱신으로 끝난다.

### 로그인 없이 앱 로컬에만 저장

채택하지 않았다. 서버 계정이 없으면 기록이 기기에만 남아, 나중에 계정을 연결할 때 옮길
대상이 앱 내부에만 존재한다. 동기화 코드를 따로 만들어야 하고 기기 변경 시 유실된다.

## 결과

### 장점

- 첫 화면에서 로그인을 요구하지 않아 이탈 지점을 제거한다.
- 승격이 컬럼 갱신으로 끝나 데이터 이전이 없다.
- 신규 코드가 엔드포인트 1개와 enum 값 1개뿐이다. 토큰·인증·보호 API는 그대로다.
- 마이그레이션이 없다.

### 비용과 주의점

- **무제한 계정 생성이 가능하다.** 인증 없이 호출되는 엔드포인트이므로, 게스트 생성에
  rate limit이 필요하다. 특히 `POST /uploads/presigned-urls`가 열려 있어 S3 비용 어뷰징 경로가 된다.
- 한 번 쓰고 버려진 게스트 행이 누적된다. 정리(purge) 배치가 후속 과제다
  (ADR 0011의 refresh 정리 배치와 함께 다룰 수 있다).
- 앱 삭제 시 refresh token이 사라져 기록을 복구할 수 없다. 온보딩에서 명시해야 한다.
- 게스트 비율이 높아지면 `member` 행 수가 실사용자 수보다 훨씬 커진다. 지표를 볼 때
  `provider`로 구분해야 한다.
