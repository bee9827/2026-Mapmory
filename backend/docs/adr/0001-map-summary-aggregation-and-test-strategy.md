# ADR 0001: 지도 요약 집계 및 테스트 전략

- 상태: Proposed
- 작성일: 2026-08-10
- 관련 이슈: #24, #25, #26

## 배경

지도 요약 API는 현재 회원의 여행 기록을 다음 세 단계로 집계한다.

1. 국가별 기록 수
2. 국가의 최상위 지역별 기록 수
3. 선택한 지역의 직속 하위 지역별 기록 수

여행 기록은 최종 선택 지역인 시·군·구를 참조하므로 최상위 지역 집계에는
`travel_record → location → parent` 계층 조인이 필요하다. 또한 기록 수에 따른
색상 단계를 일관되게 제공하고, 데이터가 늘어나도 조회 쿼리 수가 증가하지 않도록
해야 한다.

테스트에서는 집계 쿼리의 실제 동작을 검증해야 하지만, 모든 테스트에서 전체 Spring
애플리케이션 컨텍스트를 로드하면 실행 비용이 크고 이후 기능이 무거운 테스트 구조를
그대로 복제할 가능성이 있다.

## 결정

### DB에서 집계를 완료한다

- Spring Data JPA의 JPQL `GROUP BY` 쿼리를 사용한다.
- 엔티티와 연관 컬렉션을 조회한 뒤 애플리케이션에서 합산하지 않는다.
- 쿼리 결과는 국가 또는 지역 요약 projection으로 바로 반환한다.
- 각 집계 쿼리는 결과 건수와 관계없이 SQL 한 번으로 완료한다.

API 전체에서는 리소스별 오류를 구분하기 위해 회원, 국가, 지역 존재 여부를 별도로
검증한다. 따라서 요청별 쿼리 수는 다음과 같이 고정된다.

| API | 쿼리 수 |
|---|---:|
| 국가별 집계 | 회원 확인 1회 + 집계 1회 |
| 최상위 지역별 집계 | 회원 확인 1회 + 국가 확인 1회 + 집계 1회 |
| 직속 하위 지역별 집계 | 회원 확인 1회 + 국가 확인 1회 + 지역 확인 1회 + 집계 1회 |

이는 결과 행마다 추가 쿼리가 발생하는 N+1이 아니라 데이터 건수와 무관한 고정 비용이다.

### count와 이산 level을 함께 제공한다

- 원본 기록 수는 `count`로 제공한다.
- 화면 색상 단계는 `level`로 제공한다.
- 현재 단계는 `0~3`이며 기준은 다음과 같다.

| count | level |
|---:|---:|
| 0 | 0 |
| 1~2 | 1 |
| 3~5 | 2 |
| 6 이상 | 3 |

`level`은 비율이 아니라 순서가 있는 구간 값이다. 향후 연속 그라데이션이 필요하면
`level`의 의미를 변경하지 않고 `0.0~1.0` 범위의 `intensity` 필드를 별도로 검토한다.

### 테스트 계층을 목적별로 분리한다

- Controller: `@WebMvcTest`로 경로, 헤더, JSON 및 Problem Details 계약을 검증한다.
- Service: Spring 컨텍스트 없는 Mockito 단위 테스트로 검증 순서, 예외 및 응답 변환을 검증한다.
- Repository: `@DataJpaTest`로 JPQL, 계층 조인, 회원 필터와 정렬을 검증한다.
- 전체 컨텍스트: 애플리케이션 로딩 스모크 테스트 한 개만 유지한다.
- Hibernate Statistics로 각 집계가 SQL 한 번만 실행되는지 검증해 N+1 회귀를 방지한다.

## 대안

### 엔티티를 조회한 뒤 서비스에서 집계

구현은 단순해 보이지만 데이터 전송량과 메모리 사용량이 증가하고, 지연 로딩된
연관관계를 순회하면 N+1이 발생할 수 있어 선택하지 않았다.

### 모든 서비스 테스트에서 `@SpringBootTest` 사용

실제 Bean 연결을 폭넓게 확인할 수 있지만 테스트 실행 시간이 길고 실패 원인이 여러
계층에 걸쳐 모호해진다. 전체 컨텍스트 검증은 스모크 테스트로 제한한다.

### 색상 강도를 `0.0~1.0` 또는 `0~255`로 제공

연속 그라데이션에는 유리하지만 정규화 기준에 따라 같은 `count`의 색상이 달라질 수
있고 API가 렌더링 방식에 더 강하게 결합된다. 현재 단계형 지도에는 이산 level이 더
명확하다.

## 결과

### 장점

- 데이터가 증가해도 집계 쿼리 수가 일정하다.
- 집계 기준과 색상 정책을 서버에서 일관되게 관리한다.
- 테스트 실패 지점이 Controller, Service, Repository로 명확히 구분된다.
- 이후 기능이 전체 컨텍스트 테스트를 무분별하게 복제하지 않도록 선례를 제공한다.

### 단점 및 후속 작업

- 존재 확인을 위한 고정 쿼리 비용이 있다.
- 현재 Repository 테스트는 H2를 사용하므로 운영 DB가 확정되면 주요 집계 쿼리를
  Testcontainers 기반 운영 DB 통합 테스트로 추가 검증해야 한다.
- level 경계값은 운영 데이터 분포와 사용자 경험을 관찰한 뒤 조정될 수 있다.
